# Blind75 問題作成スキル

LeetCode の問題番号を受け取り、この blind75 リポジトリのカテゴリ構成に合わせて、日本語の問題ページ（HTML）と解答ファイル一式を作成する。

## 入力

- **必須**: 問題番号
  - 例: `blind75-create 190`
- **任意**: 出力先カテゴリディレクトリ（未指定の場合は `README.md` から決定する）

## 手順

### 1. 問題番号から対象問題を決定する

1. `README.md` を読み、問題表からその番号の行を探す。
2. 行の問題タイトルを使って LeetCode のスラッグを推定する。
3. スラッグは原則として、英語タイトルを小文字化し、英数字以外をハイフンに変換し、連続ハイフンを1つにまとめる。
4. 既存ディレクトリがある場合は、そのディレクトリ名の `{問題番号}-{スラッグ}` を優先してスラッグを決定する。

例: `blind75-create 190` -> `README.md` の `190. Reverse Bits` -> `reverse-bits`

`README.md` に対象行が見つからない場合、またはスラッグ推定に確信が持てない場合は、勝手に進めずユーザに確認する。

### 2. 同梱スクリプトで問題データを取得する

このスキルに同梱している `scripts/leetcode-fetch` で、LeetCode GraphQL API から問題データを取得する。
グローバルな `leetcode-fetch` コマンドや Nix 配置には依存しない。

```bash
.codex/skills/blind75-create/scripts/leetcode-fetch <slug>
```

レスポンスは JSON 形式で、以下のフィールドを含む:

- `data.question.questionFrontendId`: LeetCode 上で表示される問題番号（例: `"14"`）
- `data.question.title`: 問題タイトル（例: `"Longest Common Prefix"`）
- `data.question.titleSlug`: スラッグ（例: `"longest-common-prefix"`）
- `data.question.difficulty`: 難易度（`"Easy"` / `"Medium"` / `"Hard"`）
- `data.question.content`: 問題文（HTML 形式）

### 3. Blind 75 のカテゴリを決定する

このリポジトリでは、問題ディレクトリを `README.md` のジャンルに合わせたカテゴリディレクトリ配下に作成する。

1. `README.md` を読み、`## Array (配列)` のような見出しと、その直下の問題表を確認する。
2. `questionFrontendId` と `title` を使って、対象問題がどの見出し配下にあるかを特定する。
3. 見出しの英語カテゴリ名を小文字・スペース区切りなしのディレクトリ名に変換して、出力先カテゴリディレクトリにする。

既存カテゴリのディレクトリ名は、原則として以下に揃える:

| README 見出し | ディレクトリ |
| --- | --- |
| `Array (配列)` | `array` |
| `Binary (ビット操作)` | `binary` |
| `Dynamic Programming (動的計画法)` | `dynamic-programming` |
| `Graph (グラフ)` | `graph` |
| `Interval (区間)` | `interval` |
| `Linked List (連結リスト)` | `linked-list` |
| `Matrix (行列)` | `matrix` |
| `String (文字列)` | `string` |
| `Tree (木)` | `tree` |
| `Heap (ヒープ)` | `heap` |

例: `190. Reverse Bits` は `README.md` の `Binary (ビット操作)` 配下にあるため、作成先は `binary/190-reverse-bits/{yyyyMMdd}/`。

対象問題が `README.md` に存在しない場合は、勝手にカテゴリを推測せず、ユーザに出力先カテゴリを確認する。

同じ問題番号が複数カテゴリにある場合は、ユーザが指定したカテゴリを優先する。指定がない場合は、`README.md` で最初に見つかったカテゴリに作成する。

### 4. ディレクトリとファイルを作成する

以下の構造で作成する:

```text
{カテゴリディレクトリ}/{問題番号}-{スラッグ}/{yyyyMMdd}/
├── problem.html            # 日本語訳の問題文（図付き HTML）
├── FirstSolution/
│   ├── {問題番号}.{スラッグ}.java  # Java の解答用クラスファイル（雛形）
│   └── {問題番号}.{スラッグ}.cs    # C# の解答用クラスファイル（雛形）
└── AISolution/
    ├── {問題番号}.{スラッグ}.java  # AI による模範解答（Java、解説コメント付き）
    ├── {問題番号}.{スラッグ}.cs    # AI による模範解答（C#、解説コメント付き）
    └── explanation.html    # 模範解答の詳細解説（初心者向け・図解付き）
```

- `{カテゴリディレクトリ}`: `README.md` から決定したカテゴリディレクトリ（例: `binary`）
- `{問題番号}`: `questionFrontendId` を使用（例: `14`）
- `{スラッグ}`: API の `titleSlug` を使用（例: `longest-common-prefix`）
- `{yyyyMMdd}`: 本日の日付（例: `20260331`）

例: `./array/14-longest-common-prefix/20260331/`

解答ファイル名は LeetCode CLI の提出形式に合わせ、必ず `{問題番号}.{スラッグ}.{拡張子}` とする。スラッグには API の `titleSlug` をそのまま使う。

例: `FirstSolution/70.climbing-stairs.cs`、`AISolution/70.climbing-stairs.java`

### 5. 各ファイルの内容

#### problem.html（日本語訳の問題文）

API から取得した問題文を正確に日本語へ翻訳し、ブラウザで単体表示できる `problem.html` として作成する。問題番号、英語タイトルまたは日本語タイトル、難易度、問題文、例、制約を含める。問題のルール・操作・ゴールの関係を最初に把握できる、小さく簡潔な図を問題文の直後に添える。

問題ページは解法のヒントや模範解答を含めない。例の入力・出力・説明と制約は、原文の意味・数式・変数名を正確に保持する。

#### FirstSolution/{問題番号}.{スラッグ}.java / .cs（解答雛形）

LeetCode の問題に対応する Java と C# のクラス雛形を作成する。
API レスポンスの問題文からメソッドシグネチャを読み取り、各言語に対応した雛形を生成する。

```java
class Solution {
    // {メソッドシグネチャ（問題文から読み取る）}
}
```

```csharp
public class Solution {
    // {メソッドシグネチャ（問題文から読み取り、C# の型に置き換える）}
}
```

#### AISolution/{問題番号}.{スラッグ}.java / .cs（模範解答）

AI が作成する模範解答。Java と C# の両方のファイルを作成し、アルゴリズムの選択理由、計算量、処理の流れをコードコメントで解説する。
2 つの実装は同じアプローチ・同じ計算量に揃えること。変数名は意味が伝わる名前をつけること。ループ変数（`i`, `j`, `k`）を除き、1文字変数の使用は禁止。

```java
// 問題: {問題番号}. {タイトル}
// アプローチ: {使用するアルゴリズム・データ構造の概要}
// 時間計算量: O(...)
// 空間計算量: O(...)
class Solution {
    // {解説コメント付きの完全な実装}
}
```

```csharp
// 問題: {問題番号}. {タイトル}
// アプローチ: {使用するアルゴリズム・データ構造の概要}
// 時間計算量: O(...)
// 空間計算量: O(...)
public class Solution {
    // {解説コメント付きの完全な実装}
}
```

#### AISolution/explanation.html（模範解答の詳細解説）

`AISolution/{問題番号}.{スラッグ}.java` と `AISolution/{問題番号}.{スラッグ}.cs` で共通する考え方と処理の流れを、LeetCode 初心者でも追えるレベルで詳しく解説する、ブラウザでそのまま開ける自己完結型の HTML ページを作成する。
単に正解コードを説明するだけでなく、「なぜその発想になるのか」「他の考え方と比べて何が嬉しいのか」「各ステップで何が起きているか」まで文章で言語化する。

HTML は、次の構成を最低限含めること:

```text
<!doctype html>
<html lang="ja">
  <head>
    <!-- 文字コード、viewport、タイトル、ページ固有の CSS -->
  </head>
  <body>
    <!-- 問題番号・タイトル・短い導入 -->
    <!-- 1. 問題の整理 -->
    <!-- 2. 素直に考えるとどうなるか -->
    <!-- 3. 採用するアプローチ -->
    <!-- 4. 全体の流れとコードの読み解き -->
    <!-- 5. 具体例トレース -->
    <!-- 6. 計算量 -->
    <!-- 7. つまずきやすいポイント -->
    <!-- 必要な場合のみ、図の補助となる最小限の JavaScript -->
  </body>
</html>
```

各節で扱う内容:

1. **問題の整理**: 入力、出力、ゴール、見落としやすい制約を、箇条書きだけで済ませず文章で説明する。「何を最適化・判定・列挙するのか」「順序や重複を区別するのか」など、答えの意味を明確にする。読者が最初にルールを把握できるよう、入力・操作・ゴールの関係を示す小さな図を必ず添える。
2. **素直に考えるとどうなるか**: 初見で思いつきやすい方法を、実際にどの選択・探索・計算を繰り返すかまで文章で追う。その方法が失敗または非効率になる具体的な理由（重複する状態、探索空間の増加、境界条件、最適性を保証できない選択など）を、小さな入力に結びつけて説明する。
3. **採用するアプローチ**: 状態・データ構造・不変条件を明確な一文で定義してから、更新式または操作を導く。「なぜ前の状態だけで次を求められるのか」「候補をなぜすべて比較するのか」「初期値や番兵値がなぜ安全か」を省略しない。漸化式、ポインタ、探索範囲など、文章だけでは掴みにくい関係を図で補う。
4. **全体の流れとコードの読み解き**: 入力から出力までの手順を段階的に説明し、Java / C# の共通ロジックを上から順に読む。初期化、外側・内側のループが表す対象、条件分岐が除くケース、更新時に比較・保存する理由、最終判定の意味をそれぞれ文章で説明する。
5. **具体例トレース**: 問題文の例または小さく分かりやすい例を使い、状態変化を文章と表で逐次説明する。少なくとも一つの途中状態では、複数の候補をどのように比較して値を選ぶかを示す。必要なら変数・配列・木・グラフなどのスナップショットを添える。
6. **計算量**: 時間計算量、空間計算量、支配的な処理を説明する。どのループ・状態数・データ構造の大きさからその計算量になるかを文章で対応付ける。
7. **つまずきやすいポイント**: off-by-one、初期値、境界条件、重複処理などを具体的に説明する。採用しなかった貪欲法や単純な実装が誤る反例がある場合は、短い反例とともに示す。

説明の密度:

- 各節は見出し直後の一文だけで終わらせない。読者が「何をするか」だけでなく「なぜそうしてよいか」を追える段落を置く。
- 読者が初めてそのアルゴリズムに触れることを前提に、状態名・更新式・番兵値・ループ順序を初出時に定義する。
- 図や表の前後に、その図で確認すべき関係と、図から導かれる結論を文章で書く。
- 解説の詳しさは 322. Coin Change の `AISolution/explanation.html` を基準にする。ただし、問題の性質に関係しない説明や図を機械的に増やさない。

図解の原則:

- **文章が主、図が従**。各節は必ず、理解に必要な文章を先に置き、その直後に文章を補う図を置く。図だけで説明を済ませない。
- 図は「一つの関係を一目で伝える」最小限のものにする。装飾的なカード、過剰な色、情報量の多いダッシュボードにはしない。
- 問題の整理には必ず図を置く。以降も、アルゴリズムの核・データ構造の状態・具体例の遷移など、視覚化が理解を明確に改善する箇所にだけ図を置く。
- HTML/CSS で、配列・ハッシュマップ・連結リスト・木・スタック・キュー・グラフ・探索範囲などを問題に合う形で描画する。外部の画像や CDN、Mermaid には依存しない。
- 図には短いキャプションを付け、「何を表しているか」と「文章のどの説明を補うか」を明示する。
- 操作型の図は、状態遷移の確認に実際に役立つ場合だけ JavaScript で追加する。操作型の図は具体例トレースの後に置き、本文を読む流れを妨げない補助にする。

問題ページと解説ページの共通デザイン:

- `problem.html` と `AISolution/explanation.html` は同じ視覚システムで作る。背景色、本文色、罫線色、アクセント色、コード表示、見出しの書体・余白を揃え、ページを行き来しても同じ教材として読めるようにする。
- 両ファイルの CSS に、少なくとも次の共通トークンを同じ値で定義する。

```css
:root {
  --ink: #1f2937;
  --muted: #596579;
  --line: #dbe2ea;
  --paper: #fff;
  --canvas: #f6f8fb;
  --blue: #2563eb;
  --blue-pale: #eff6ff;
  --orange: #c2410c;
  --orange-pale: #fff7ed;
}
```

- 問題ページは問題文を読むことに、解説ページは解法を読むことに集中させる。用途に応じた図の違いは許容するが、別サイトのような配色・過剰な装飾・異なる UI パターンを使わない。

実装上の要件:

- CSS と JavaScript は `problem.html` および `explanation.html` にインラインで含め、各ファイル単体で閲覧可能にする。
- 外部ライブラリや外部アセットを使わない。したがって、原則として Flake への依存追加は不要である。ローカル確認用の静的サーバーなど、追加ツールを実際に導入する場合だけ `flake.nix` に最小限の依存を追加する。
- レスポンシブにし、モバイル幅でも本文と図が読めることを確認する。
- 色だけに意味を持たせず、ラベル・見出し・キャプションも使って状態を伝える。

### ルール

- 問題文の日本語訳は正確に翻訳する。意訳は最小限にとどめる
- コード例、変数名、データ構造名（例: `nums`, `ListNode`）は原文のまま残す
- 数式や数値条件もそのまま保持する
- API の HTML タグは意味を保ったセマンティックな HTML に変換する（`<code>` は `<code>`、`<sup>` は `<sup>` として扱う）
- `FirstSolution/{問題番号}.{スラッグ}.java` と `FirstSolution/{問題番号}.{スラッグ}.cs` のメソッドシグネチャは問題文中のコード例から正確に読み取り、それぞれの言語の型・構文に合わせる
- Java / C# のすべての解答ファイルは `{問題番号}.{スラッグ}.{拡張子}` の名前にする。これにより `leetcode submit <ファイルパス>` で直接提出できる
- C# の解答ファイルは LeetCode 提出形式に合わせ、`Main` メソッド、テストコード、標準入出力処理を含めない
- AISolution の Java / C# は同じアルゴリズムを、それぞれの言語で自然な構文に落とし込んで実装する
- `problem.html` は問題文・例・制約だけを扱い、解法や解説を含めない。`AISolution/explanation.html` と共通デザインのトークンを使用する
- `AISolution/explanation.html` は、文章を主役にし、問題に合った HTML/CSS の図と具体例トレースで理解を補う。LeetCode 初心者を読者として、用語の飛躍を避けて丁寧に説明する
- `AISolution/explanation.html` は外部依存なしで表示できることを確認する。必要に応じてローカル静的サーバーで開き、文章・図・操作要素がモバイル幅でも読みやすいことを確認する
- 作成後、対象問題の `README.md` の進捗欄は必要に応じて更新する。既存の進捗記号や周回の意味が不明な場合は、勝手に変更せずユーザに確認する
- skill 完了時、これからユーザは問題を解くので模範解答についてユーザに伝えないこと
